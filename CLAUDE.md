# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

NestJS 12 API on Express, TypeORM 1.x with MySQL 8 (`mysql2` driver), zod 4 for env and request validation, `@nestjs/jwt` for auth, `@casl/ability` for authorization, `@nestjs/swagger` for API docs, `nestjs-i18n` for translated messages, `nestjs-cls` for request context, `@nestjs/throttler` for rate limiting, `helmet`, `@nestjs/terminus` for health checks, `@azure/storage-blob` for file storage (Azurite emulator in development), `@nestjs/event-emitter` for in-process events, TypeScript 6, Vitest for tests, oxlint for linting, Prettier for formatting.

## Setup

Copy `.env.example` to `.env` before running anything on the host. The defaults there point at the MySQL container from `docker-compose.yml` (host port 3308).

## Commands

```bash
npm run start:dev          # watch mode
npm run build              # nest build -> dist/
npm run lint               # oxlint --type-aware src/ test/
npm run format             # prettier --write on src/ and test/

npm test                   # unit tests (**/*.spec.ts)
npm run test:e2e           # e2e tests (**/*.e2e-spec.ts), separate vitest config
npx vitest run src/modules/health/queue.health.spec.ts  # single file
npx vitest run -t "test name"               # single test by name

docker compose up          # app (host :3001 -> 3000) + MySQL (host :3308 -> 3306)

npm run i18n:types         # regenerate src/generated/i18n.generated.ts after editing src/i18n/*/*.json
npm run i18n:check         # fails if a language is missing a key
```

Install packages inside the container with `docker compose exec app npm install --include=dev <pkg>`: npm there omits dev dependencies by default, so a plain `npm install` removes oxlint, vitest and the Nest CLI. Then `docker compose restart worker`. Files created inside the container (e.g. by `i18n:types`) are owned by root; `chown` them back to your user.

### Migrations and seeding

The only npm script is `npm run migration` (runs pending migrations; it does not build first, so `dist/` must be current, and it works inside the production image too). For everything else run the tools directly, usually inside the container (`docker compose exec app <command>`, or `docker compose exec app sh` for a shell). `synchronize` is off, so every schema change needs a migration. The TypeORM CLI needs the compiled data source, so run `npx nest build` first (inside the container, `docker compose exec app ...`, so `dist/` is not created with the wrong owner) and re-run it after changing entities or migrations.

```bash
npx nest build   # wipes and rebuilds dist/, which the watch-mode app also runs from: run `docker compose restart app` afterwards
npx typeorm migration:generate -d dist/database/data-source.js src/database/migrations/<Name>  # diff entities against the DB (add --check to only detect drift)
npx typeorm migration:create src/database/migrations/<Name>                                      # empty migration
npx typeorm migration:run -d dist/database/data-source.js
npx typeorm migration:revert -d dist/database/data-source.js
npx typeorm migration:show -d dist/database/data-source.js

node dist/cli/cli.js seed              # roles, permissions, first super admin (idempotent); add --dry-run to preview
```

## Architecture notes

- **ESM project** (`"type": "module"`, `module: nodenext`). Relative imports must use the `.js` extension, even from `.ts` files (e.g. `import { HealthController } from './health.controller.js'`). Top-level `await` is used in `main.ts`.
- **URL prefix.** This is an API-only app: every route is served under `/api` except `GET /health` and `GET /health/live` (public, no prefix) and Swagger UI at `/docs`. The prefix, Helmet, CORS and trust proxy are configured in `src/app.setup.ts` (`configureApp`), which both `main.ts` and the e2e tests call, so new test apps must call it too. New routes need no extra work; never hard-code `/api` in controllers.
- **Roles and hierarchy.** Five roles with numeric levels (`src/common/enums/role-name.enum.ts`): `super_admin` 100 > `admin` 80 > `manager` 60 > `site_incharge` 40 > `site_technician` 20. A user can only create or manage users with a strictly lower level. Only `super_admin` has `manage all`, so only it can create other super admins or admins. Everyone except `admin` can only manage accounts they themselves created (`createdById`). Any role can read itself.
- **Permissions are data, scoping is code.** `src/database/seeds/role-permissions.ts` is the single source of truth for each role's `(action, subject)` pairs. The seeder syncs them into the `roles`, `permissions` and `role_permissions` tables. `CaslAbilityFactory` (`modules/authorization/`) reads the actor's role permissions and attaches the hierarchy conditions (`role.level`, `createdById`). To change what a role can do, edit `role-permissions.ts`, rebuild and run the seed command. To change the scoping rules, edit the factory. `readableUsersWhere` in the same file is the TypeORM version of the 'read' rule for list queries (users list and the audit log), so keep them in sync.
- **Users and Sites depend on each other.** `SitesService` uses `UsersService.findOneFor` to check a site's in-charge (`sites.inchargeId`, must have the `site_incharge` role and be in the actor's user scope), and `UsersService.remove` asks `SitesService` whether the user is still in charge of a site (409 if so). Both sides use `forwardRef`: in the module `imports` and as `@Inject(forwardRef(() => X)) x: Pick<X, 'method'>` in the constructors. In ESM a plain type there makes `emitDecoratorMetadata` read the class before the import cycle has initialized it (`ReferenceError: Cannot access 'X' before initialization`). Prefer a third module or a one-way call over adding new cycles.
- **Two layers of authorization.** `@CheckAbility('create', 'User')` plus `PoliciesGuard` answer "does this role have the permission at all". Services then check the specific record with `ability.can(action, subject('User', target))`. Out-of-scope records return 404, not 403, so ids are not revealed.
- **Auth.** `JwtAuthGuard` is registered globally (`APP_GUARD` in `AuthModule`), so every route needs a bearer access token unless marked `@Public()`. It loads the user fresh on each request, so role changes apply immediately. Access and refresh tokens use separate secrets and expiries from env. The refresh token is rotated on each use and stored hashed (`users.refreshTokenHash`). Logout clears it. Passwords and refresh tokens are hashed with Node's built-in scrypt (`common/security/secret-hash.ts`). `password` and `refreshTokenHash` are `select: false`, so queries must opt in with `addSelect`. Email verification is stored (`emailVerifiedAt`) but not enforced at login. `password` is nullable: a user created through the API has none until they accept the invitation, so login treats a null password as invalid credentials.
- **Invitations and first password** (`modules/invitations/`). `POST /api/users` takes no password. `UsersService.create` emits `user.created` (`users/events/`); `UserCreatedListener` (`@OnEvent(..., { async: true })`, catches and logs, never throws) calls `InvitationsService.send`: a `generateToken()` token whose `hashToken()` SHA-256 is stored in `users.inviteTokenHash` (indexed, 72 h `inviteExpiresAt`), and a `mail.send-invite` job with `<APP_URL>/set-password?token=...`. `POST /api/invitations/accept` (public) sets the password, `emailVerifiedAt` and clears the token in one conditional UPDATE. `POST /api/users/:id/invitation` resends (update rule via `UsersService.findOneToUpdate`; 409 once a password exists). An email change clears the invite token with the other verification state and emits `user.email-changed`; `InvitationListener` re-invites the user at the new address only while `InvitationsService.isPending`. `InvitationsModule` imports `UsersModule`, never the reverse: users only emit the event.
- **Password policy** (`common/security/password-policy.ts`). Use `passwordSchema` for every password that is SET (invitation, admin update), never for login: 8+ chars, capital, small letter, digit, symbol, each with its own `errors.password.*` key. `assertPasswordAvoidsNames(password, [firstName, lastName])` must be called wherever a password is set, because the schema cannot see the user's names; names under 3 letters are ignored.
- **Optional MFA** (`auth/mfa.service.ts`). `users.mfaEnabled` (self-service `PUT /api/auth/me/mfa`, password required). Login of an MFA user returns `{ mfaRequired, challengeToken }` and queues `mail.send-login-otp` (code hashed in `mfaOtpHash`; one 10-minute window per user with 5 attempts in total: a new login inside the window keeps `mfaOtpExpiresAt` and `mfaOtpAttempts`, and an exhausted window answers 429 `errors.mfa.locked`; attempts are claimed with a conditional increment like the email OTP); `POST /api/auth/login/mfa` exchanges challenge + code for tokens. The challenge is a JWT with `typ: 'mfa'` signed with the access secret, and `JwtAuthGuard` rejects that type: keep that check if the guard changes.
- **Roles cache.** `RolesService.findAll()` caches `{ id, name, level }` for all roles (`@nestjs/cache-manager`, in-memory, 1 hour TTL) and backs `GET /roles` and the role lookup in `UsersService.create`. Roles change only when the seed command runs; the cache is per process, so restart the API (a normal deploy does) or wait out the TTL after reseeding. It does not cache the role a user is loaded with per request (eager relation in `UsersService.findById`).
- **Email verification.** `JwtAuthGuard` also rejects (403 `Email is not verified`) any authenticated request from a user whose `emailVerifiedAt` is null, unless the route has `@AllowUnverifiedEmail()` (the OTP routes, `me`, `logout`). Login itself still works and returns tokens. `POST /api/auth/email-otp/send` creates a 6-digit OTP (never equal to the previous one), stores only its scrypt hash on the user (`emailOtpHash`, expiry 10 min, max 5 wrong attempts) and enqueues a mail job; every send overwrites the previous OTP, so only the latest is valid. `POST /api/auth/email-otp/verify` checks it and sets `emailVerifiedAt`. Changing a user's email through `PATCH /users/:id` resets `emailVerifiedAt`. Users that existed before verification was enforced were marked verified by a migration (`BackfillEmailVerifiedAt`); the seeded super admin is created verified.
- **Background jobs (RabbitMQ).** One queue (`jobs`) carries every job type as an envelope `{ id, type, payload }` (`modules/jobs/`). The API only publishes (`JobQueueService.publish(type, payload)`, resolves after the broker confirms). A separate worker process (`src/worker.ts`, `JobsWorkerModule` root: `npm run start:worker:dev`, production `node dist/worker.js`) consumes it and runs the `JobHandler` registered for the type. Run the worker on its own server; any number of workers is safe because RabbitMQ gives each message to one consumer. To add a job: add its payload to `JobPayloads` (`job.types.ts`), write a handler class, add it to `JobsWorkerModule` (provider plus the `JOB_HANDLERS` inject list). A message is acked only after the handler finishes, so delivery is at least once: handlers must be safe to run twice. A failed job is republished to `jobs.retry.5000ms`, then `30000ms`, then `300000ms` (TTL queues that dead-letter back into `jobs`), 4 attempts in total, then lands in `jobs.dead` with `x-last-error`; unknown types and malformed messages go straight there. Watch `jobs.dead` and replay by hand from the management UI. Queues are quorum queues, declared by both the API and the worker on connect. Mail is the first job (`mail.send-email-otp`, `modules/mail/`, nodemailer with 10s connect timeouts). docker-compose adds `rabbitmq` (AMQP host :5672, UI http://localhost:15672, ims/ims), `worker` and `mailpit` (SMTP :1025, inbox UI http://localhost:8025). No health checks are defined for these. After a dependency change run `docker compose restart worker`, because it does not run `npm install` itself.
- **Queue and mail settings.** `RABBITMQ_URL` (and optional `WORKER_CONCURRENCY`) in `config/rabbitmq-env.ts` is needed by the API and the worker; `MAIL_*` in `config/mail-env.ts` by the worker only (`MAIL_USER`, `MAIL_PASSWORD`, `MAIL_SECURE` are optional, for a real SMTP provider). `MailModule` is a dynamic module: `JobsWorkerModule` maps `mailEnv` into `MailModule.forRoot(options)`, and `MailService` receives them through the `MAIL_OPTIONS` token instead of reading env itself, so tests pass options directly. Production sets real values, including the broker password inside `RABBITMQ_URL` (`amqps://` for TLS), through environment variables only.
- **Request logging** (`common/logger/`, pino-http). Every line has method, url, status, time and, when authenticated, `userId` and `role`. Body logging depends on env: `NODE_ENV=development` logs request body, query and response body on every request; anything else (production, or `NODE_ENV` unset) logs metadata only. In production `LOG_REQUEST_BODY=true` adds the request body and query of every request, to debug a failing API; response bodies are never logged outside full mode. docker-compose passes `NODE_ENV` from `.env` (default `development`), so `.env` is the one place to switch it; a value hard-coded in compose would override `.env`. Changing it needs a restart: `docker compose up -d app worker` (plain `restart` keeps the old environment). `maskSecrets` replaces any property whose name matches password/secret/token/otp/hash/authorization/cookie/api key, at any depth, in everything it logs, so a new secret field must follow that naming or be added to the pattern.
- **Custom commands** use `nest-commander`. `src/cli/cli.ts` is the CLI entry point (like `main.ts`), `src/cli/cli.module.ts` lists the commands, and each command is a `@Command()` class extending `CommandRunner` in `src/cli/`. Commands get normal dependency injection (e.g. `DataSource`). To add one: write the class and add it to `providers` in `CliModule`. Production runs the compiled file: `node dist/cli/cli.js <command>`. Deployment order: `npx nest build`, `npx typeorm migration:run -d dist/database/data-source.js`, then `node dist/cli/cli.js seed`. The seed logic itself lives in `src/database/seeds/seed.ts`. It never auto-generates migrations: after changing an entity, run `migration:generate`, review the file, then run it.
- **Docker.** `docker-compose.yml` is development only (bind mount, watch mode, MySQL). The `Dockerfile` is production only and copies no `.env`, `node_modules` or `dist` from the host (see `.dockerignore`): dependencies are installed (`npm ci`) and the app is compiled inside the image, in three stages (compile, prod-only `node_modules`, runtime). It runs as the non-root `node` user with `node dist/main.js`, has a `HEALTHCHECK` on `/health/live`, and relies on `app.enableShutdownHooks()` (in `app.setup.ts`) so `docker stop` is instant (without it a PID 1 Node process ignores SIGTERM and is killed after 10s). All configuration comes from environment variables at run time; with none set the container exits with `Invalid environment variables`. The same image runs the other tasks by overriding the command: `node node_modules/typeorm/cli.js migration:run -d dist/database/data-source.js` and `node dist/cli/cli.js seed`. `typescript` and `prettier` appear in the runtime `node_modules` only because `nest-commander` depends on them.
- **Deployment**: `.github/workflows/ci-cd.yml` builds and pushes the production image on pushes to `master`; the Azure DevOps hand-off and `azure-pipelines.yml` steps are commented out for now (see README §3.4). Migrations must stay backward compatible because an old version keeps serving while the schema changes.
- **Folder layout** (`src/`):
  - `entities/`: every TypeORM entity, one `<name>.entity.ts` per table, all extending `BaseEntity` (`base.entity.ts`: id and timestamps). Entities are never placed inside feature folders.
  - `modules/<feature>/`: everything a feature needs, kept together: `<feature>.module.ts`, `.controller.ts`, `.service.ts`, `dto/` (a zod schema plus its `z.output` type per file), and its specs. A feature imports the entities it needs with `TypeOrmModule.forFeature([...])` and is registered in `AppModule`.
  - `modules/storage/`: global blob storage module, used by features (avatars now).
  - `common/`: cross-feature code (zod pipe and `idParamSchema`, i18n module/filter/`i18nMessage`, Swagger setup, logger). `config/`: validated env. `database/`: data source and `migrations/`. `i18n/<lang>/*.json`: translations (copied to `dist/` as assets by `nest-cli.json`). `generated/`: generated i18n key types, never edited by hand.
- **One shared data source config.** `src/database/data-source.ts` exports `dataSourceOptions`, which `TypeOrmModule.forRoot` in `AppModule` uses. Its default export is the `DataSource` that the TypeORM CLI loads. Entities and migrations are found by globs over the **compiled** output: `entities/*.entity.js` and `database/migrations/*.js`, resolved from `import.meta.dirname`. So entity files must be named `*.entity.ts` and live directly in `src/entities/`, and the app has to be built before running the CLI.
- **Env vars are validated at import time, split by what needs them** (zod, no fallback defaults; a missing or invalid variable throws and names it). `src/config/parse-env.ts` loads `.env` from the working directory if it exists (variables already in the process environment win) and parses. `db-env.ts` (`DB_*` incl. `DB_SSL`) is used by the data source, so migrations and the seed command need only `DB_*`. `env.ts` adds the `JWT_*` settings and `APP_URL` (frontend base URL for invitation links), plus the optional `CORS_ORIGINS`, `SWAGGER_ENABLED`, `TRUST_PROXY` and `MAIL_HOST`/`MAIL_PORT`/`MAIL_SECURE` (only for the SMTP health check; defined inline, because importing `mail-env.ts` would make the API require every `MAIL_*`), and is used by the API only. `seed-env.ts` (`SEED_SUPER_ADMIN_*`) is read lazily, only when no super admin exists yet. Add each new variable to the schema that owns it and to `.env.example`. `DB_SSL=true` turns on TLS for managed databases that require it. Optional `DB_SSL_CA` is the path to a PEM file with the CA certificate(s) used to verify the server (without it, Node's built-in trusted authorities are used).pem`. `PORT` is read directly in `main.ts` and defaults to 3000.
- **Request validation uses zod, not class-validator**, through Nest 12's Standard Schema support. A DTO file exports the schema and its type (`export const createItemSchema = z.object(...)`, `export type CreateItemDto = z.output<typeof createItemSchema>`), and the controller declares the schema on the parameter: `@Body({ schema: createItemSchema }) dto: CreateItemDto`, `@Query({ schema })`, `@Param('id', { schema: idParamSchema }) id: number`. Import the type with `type` (`import { createItemSchema, type CreateItemDto }`), as `isolatedModules` plus decorator metadata requires. `ZodValidationPipe` (`src/common/zod/`, global `APP_PIPE`) validates any parameter whose `schema` is a zod schema and returns the parsed output, so coercions and transforms apply. On failure it throws a 400 `{ statusCode, error, message, errors: [{ path, message }] }`. Swagger reads the same schema, so give **every body field an `.meta({ example })`** (or a `.default()`) that passes the schema; `src/common/swagger/swagger-examples.spec.ts` fails otherwise. For PATCH bodies set one object-level example with harmless changes only. Leave `:id` params without examples so Swagger never pre-fills a DELETE.
- **i18n.** `AppI18nModule` (`common/i18n/`): English (fallback), Hindi, Gujarati, resolved per request from `?lang=` then `Accept-Language`. Never throw English text: throw `new XException(i18nMessage('errors.some.key', { args }))` (keys typed from `src/generated/i18n.generated.ts`), and add the key to every `src/i18n/<lang>/errors.json`, then run `npm run i18n:types`. `I18nExceptionFilter` (global `APP_FILTER`) translates any `message` or `errors[].message` that starts with `errors.`; other messages pass through. Custom zod messages must also be keys (`'errors.otp.format' satisfies ErrorKey`); zod's built-in messages use its locale for the request language. Success messages use `@I18n() i18n: I18nContext<I18nTranslations>` and keys under `messages.`. A new language needs its folder, its entry in `LANGUAGES` (`languages.ts`) and its zod locale in `ZodValidationPipe`.
- **Swagger** (`common/swagger/swagger.ts`) is served at `/docs` only when `SWAGGER_ENABLED=true`. Protected controllers get `@ApiBearerAuth()`, and each route gets an `@ApiOperation({ summary })`. `withFreshExamples` swaps in a fresh email and site code (and the `site_technician` role id) on every page load. If you add a create route whose body has a unique field, add it there.
- **Rate limiting and security headers.** Global `ThrottlerGuard` (`APP_GUARD` in `AppModule`): 100 requests/min per IP, tightened on auth routes with `@Throttle`, skipped with `@SkipThrottle`. Storage is in memory per process. Over the limit the response is a translated 429. Helmet runs in `configureApp`. CORS is enabled only when `CORS_ORIGINS` is set.
- **Response depth is 1.** Every read that feeds a response (lists, get-one, and the record returned after create/update) spreads `depthOne(repository)` (`common/typeorm/depth-one.ts`) into its find options: the entity's own columns plus its to-one relations, never theirs (a user's `role`, not `role.permissions`). A related user is only a summary (`id`, names; `SUMMARY_COLUMNS` in the same file), because the full record is behind the users read scope; add other entities there if they hold data that is scoped the same way. It turns eager loading off, because eager relations such as `User.role` → `Role.permissions` would otherwise go deeper. To-many relations are not included; load one explicitly only when a screen needs it. The exception is `UsersService.findById` (auth guard, login, `me`), which keeps the eager chain because `CaslAbilityFactory` needs the permissions.
- **File storage** (`modules/storage/`). `StorageModule.forRoot(options)` is built with `ConfigurableModuleBuilder` (`storage.module-definition.ts`, so `forRootAsync` works too), registered once and global in `AppModule` from `config/storage-env.ts` (`AZURE_STORAGE_CONNECTION_STRING`, `AZURE_STORAGE_CONTAINER`, optional `AZURE_STORAGE_PUBLIC_URL`, required by the API). `BlobStorageService.upload(name, buffer, contentType)` returns the public URL to store in the DB; names must be unique (blobs are cached for a year), e.g. `users/<id>/<uuid>`. `deleteByUrl` is best effort. The container is created lazily on the first upload with anonymous blob read access. Avatars: `PUT /users/:id/avatar` (multipart field `file`) and `DELETE /users/:id/avatar` (204, idempotent), self or the update rule; no avatar is `avatarUrl: null` and the client shows its own placeholder (never store a default URL per user); checked in three layers: size (`AVATAR_MAX_BYTES`, 500 KB, Multer limits in `AvatarUploadInterceptor`, which re-throws the 413 with a translation key), then `avatarFilePipe()`: Nest's `FileTypeValidator` (PNG/JPEG from magic numbers via `file-type`, `overrideMimeType` so the stored content type is the detected one; 415) and `ImageContentValidator` (`common/files/`, uses `sharp`: no bytes after the end marker, at most 4096 × 4096, full strict decode; 422). Never re-encode or resize. Reuse `ImageContentValidator` for any future image upload. `Express.Multer.File` needs `multer` in `tsconfig.json` `types`. docker-compose runs `azurite` (blob :10000) and passes the API a connection string to `azurite:10000` plus `AZURE_STORAGE_PUBLIC_URL=http://localhost:10000/devstoreaccount1`, so stored URLs open in the host's browser.
- **Audit trail** (`modules/audit/`, table `audit_logs`). `AuditSubscriber` (TypeORM subscriber, registers itself on the `DataSource`) records every insert, update and remove made with `save()` / `remove()` in the same transaction, with the actor, request id and IP from `nestjs-cls` (`ClsModule` in `AppModule`; `JwtAuthGuard` sets `actor`; store type `common/context/app-cls.ts`). Rules: business changes must use `save({ id, ...changes })` / `remove(entity)`, never `repository.update(criteria, values)` or a QueryBuilder update (TypeORM does not tell subscribers which row those changed); keep `update()` for technical state, or call `AuditService.record(entry, manager)` inside the transaction when an atomic conditional update matters (as `InvitationsService.accept` does). Mark technical columns `@NotAudited()` (`common/audit/`); secret-looking names are masked by `maskSecrets`. `GET /api/audit-logs` needs `read AuditLog` (admin, seeded) and filters `User` entries with `readableUsersWhere`, so keep that rule in sync there too. The seed command is not audited (CliModule does not load AuditModule).
- **Health checks** (`modules/health/`, Terminus). `GET /health` reports `database`, `rabbitmq`, `worker` (consumers on the `jobs` queue), `storage` (blob account answers) and `mail` (SMTP 220 greeting, only when `MAIL_HOST`/`MAIL_PORT` are set for the API) separately, 503 if any is down, 3 s timeout each. `GET /health/live` is liveness only and is what the Docker `HEALTHCHECK` calls. A new external dependency should get a check here.
- **TypeScript**: `strict` is on and `strictPropertyInitialization` is off, so entity and DTO class properties don't need initializers. Vitest globals are enabled (`describe`/`it`/`expect` need no import).
- **Lint**: oxlint treats `typescript/no-floating-promises` as an error, so every promise must be awaited or handled. `any` is allowed. A Claude Code `PostToolUse` hook (`.claude/settings.json` → `.claude/hooks/format-lint.sh`) runs `npm run format` then `npm run lint` inside the app container (`docker compose exec -T app ...`) after every Write or Edit of a `.ts` file under `src/` or `test/`. Lint errors, or the app container not running, come back as blocking feedback, so fix them before moving on.
- **README.md** is the software design write-up (architecture, flows, API surface, production setup, design decisions). Keep it in sync with design changes and new features; a Stop hook (`.claude/hooks/readme.sh`) asks for this when entities, migrations, modules, controllers, DTOs, config, entry points, Docker/CI files or dependencies changed after the README did.
- **Prettier**: single quotes, trailing commas everywhere.
- **Comments**: write them sparingly. Do not comment code that reads clearly on its own, and do not restate what the code does. Add a comment only when the code is tricky or non-obvious, or when it affects other modules (e.g. a rule that must be kept in sync elsewhere). Keep it short and explain why, not what. When touching a file, remove comments that no longer earn their place.
